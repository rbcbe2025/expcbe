# Evals

The cases `claude plugin eval` grades (Claude Code 2.1.269 or later). They live here, outside the plugin, so an install
never carries them: `cases/<skill>-<id>/`, generated by the repository's `scripts/gen-evals.mjs` from each skill's own
evals and never edited by hand; `mocks/` is hand-written; `results/` (ignored by git) is where runs write their reports,
`index.json` and `gradings.json`. A run copies the plugin and the cases it needs into a temporary folder
(`scripts/run-evals.mjs`), where the suite sits as `evals/` below the plugin, as the CLI expects.

## What a case holds

- `prompt.md`: the prompt, verbatim, with the case's frontmatter. Every case may use Read, Glob, Grep, Skill, Write, Edit
  and Bash; the last three are granted by the operator (`--allow-tools`), as `scripts/run-evals.sh` does.
- `graders/assertion-NN.md`: one grader per assertion of the skill's eval, so a run scores the fraction of assertions it
  meets and the report names the ones it missed. `graders.json` grades an assertion for free where that was proved or is
  plain: a regex over the final message (46 patterns from the archived skill-creator specs, each giving the judge's
  verdict on every recorded run; a few hand-written ones, each with its reason), a `file_exists`, or the judge pointed at
  the file itself (the trace shows a judge only the first and last 12 messages, so a file written mid-run is invisible
  to it); six assertions that passed in every run with and without the plugin are dropped. Most others are `llm` graders
  over the run's trace (the judge votes three times;
  two passes pass). The assertions about tool calls are `tool_used` or `tool_order` graders instead, from the repository's
  `evals/checks.json`: the judge sees a long run's trace with its middle elided, so a call made mid-run is invisible to it,
  while those graders read every call. A list in `checks.json` splits the assertion into `assertion-NNa.md`,
  `assertion-NNb.md` with half the weight each.
- `graders/uses-skill.md`: a `tool_used` grader for `Skill` on the cases whose prompt names the skill. Under the
  with/without comparison it is an indicator, not part of the score.
- `case.yaml`, `scaffold.sh`, `fixture/`: on the cases whose prompt takes files for granted ("my package", "my app in
  app/", "the upload passed"). The scaffold copies the fixture into the run's working directory before the agent starts
  (`--scaffold`). The fixtures are the repository's `evals/fixtures/` (its README says what each one is).
- `mocks/cloudbackend-tenant/_server.md` on the two sign-in cases: the tenant stand-in starting signed out.

Case ids follow the 2026-11-07 merge (cloudbackend-saas-launch absorbed the workflow's cases as 7 to 17, xios3-app-basics
the design cases as 4 to 11); the hub's `_skills/_archive/2026-11-07-merged-skills/case-map.json` maps each old id to its
new one. The two built-in-browser points of the old workflow case 12 left with it (they need the Claude desktop app).

## The servers in a run

| Server | In a run | Why |
| --- | --- | --- |
| cloudbackend-tenant | `mocks/cloudbackend-tenant/`: an `agent` stand-in (a model answers each call in the real server's shapes, from `_server.md`'s account `acme` with the project `tasktrack`); `_tools.json` is the real server's tools/list, refreshed by gen-evals | it signs in, uploads and deploys: no run may reach CloudBackend. The stand-in starts signed in (the deploy cases take an earlier sign-in for granted). Its `abort_when` ends the run with score 0 when a password, a token or a key reaches a call, when `enable_deploy_connector` is called (an account change nobody said yes to), or when `upload_project` skips lint |
| cloudbackend-docs, cloudbackend-build | the plugin's real servers (`--allow-real-servers`, their tools granted by name) | this repository's own read-only code: the docs server reads the public portal, the build server lints the files it is given. A mock would make the lookups up |

Agent stand-ins record their answers under `results/<run>/mock-recordings/` with an `ADOPT.txt`; copying a recording into
`mocks/.replay/` (or a case's `mocks/.replay/`) makes later runs replay it without a model call. None are adopted yet.

## Running it

On big (Claude Code 2.1.316), from the repository: `scripts/run-evals.sh <label>` runs what `node scripts/eval-plan.mjs`
selects, on Opus 5.5 with the Haiku 5.5 judge:

- a case runs when its skill's content hash, its own files or the plugin's servers, agents and stand-ins changed since
  its last run on that model (`results/index.json`); a saturated case (`tiers.json`) only when its skill changed;
- a case whose files changed, or that has no stored baseline for the model, runs with and without the plugin and
  stores the without score (`baselines/without-<model>.json`); the rest run with the plugin only and read their delta
  against that stored score (it moved by 0.2 or less on 34 of 40 cases across every recorded run);
- `--all` runs every case (monthly), `--case NAME` picks cases, `--runs N` repeats them, `--max-cost-usd` caps both
  passes together, `--model claude-fable-5-1 --with-only` is the release's second model.

The release (stage e) runs both passes. `node scripts/eval-report.mjs results/<file>.json` prints any recorded run.
The CLI has no setting for the judge's three votes; `--shadow-focus` adds, in the temporary copy only, a with-only twin
of each trace judge that reads the final message, to find the graders that can judge the cheaper target unchanged.

runs select by hash, reuse a stored without-plugin baseline, and default to Opus 5.5 (Fable 5.1 at release). 55
assertions are graded for free (regex or file), 3 judges look at a cheaper or truer target, 6 always-passing assertions
