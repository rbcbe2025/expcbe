## Create Identity

### Creating a new identity

In figure 1 we can se the `Create` button in the toolbar for creating a new identity. Identities are one of the most important concepts in CloudBackend as all data created in the database is tied to the identities that created it, let it be an end-user, IoT sensor, or a backend API logged in as an identity. It is therefore important to not think of `Identity` as not only a user, but potentially anything that needs authenticated access to the database.

> **Tip:** Create identities for each developer, data scientist, support personnel, billing responsible, and internal staff that should have access to the database. Remember to assign correct roles and ACLs to them. Identity accounts created by an external deployed and published application will default have no role assigned to them, they are the end-users of a SaaS application built on top of CloudBackend. Identities without a role assigned will not be allowed to login to the database.


In figure two we see the `Create Identity` window and its form for filling out the information required. If you need to programmatically import a large set of users from an existing organization (LDAP, ActiveDirectory etc), please use the SDK Mobile, IoT & Cloud for that purpose.


> **Note:** The owner of the tenant (an organization or individual) is legally responsible for all the tenant identities created. It is recommended to have each identity created externally to have agreed to an End-user License Agreement (EULA) similar to the EULA accepted by logging into the CloudBackend database.

## Create Role

### Creating a new role

Now when you have created a new `identity`, the next step is to create a new `role`. In figure 3, click the Manage Roles button to get the `Manage Roles` application to show. Please note that an identity without an assigned role will not be able to login to the database (they will be considered an end-user of a SaaS application with no business to login to the database).


When the `Manage Roles` application is open it displays all roles configured for the tenant in the list, it should always have the default `Owner` and `Administrator` roles, which can not be renamed or deleted. You can neither change the behavior of the default roles since they are generated by the system and have special meaning. In the following figure 4, the `Manage Roles` application is visible.


Please note the Create... button, which is used to create a new role. Figure 5 shows the Create Role prompt itself.

> **Tip:** Use descriptive names of roles like `Developer`, `Tester` etc. that describes what the role is supposed to do.


> **Tip:** End users will normally not be assigned to any role like these, but will use a dedicated deployed application.

## Configure Group

Groups may be mounted and explored in the `Database Explorer` through the `Mount...` button. This will mount a new `database` with the same name in the `Database Explorer` section. This allows for the partitioning of data between groups.

Once the group has been mounted a `Login...` button will be visible. This will open a window in which group configuration can be performed.

> **Tip:** By navigating to the `Personal` tab you may set the group to be auto-mounted for your account when you log in to the dashboard.

The group details window allows for various configuration of the group. The group `description` and `icon` is displayed to invited users when viewing their invitation. `Keywords` allow for the group to be found by filtering by keywords.

> **Warning:** Keywords are currently not supported as searchable terms in the CloudBackend dashboard.

## Create Group

In figure 1 we can see the `Create Sub-Group...` button for creating a new group directly under the `tenant` group. [Groups](https://robinsbackend-robinsbackend-portalx.cloudbackend.cloud/cloudbackend/docs/database/the-singularity/get-to-know/concepts/group) allow you to partition data within the database, creating logical separations for different projects, teams or applications.

> **Note:** Sub-groups may contain other sub-groups, and are not limited to being directly under the tenant group.


When the `Create Group` application is open it allows for the configuration of group settings as the group is created. The `alias` field may be omitted, in that case the users alias will default to the alias of the tenant group. If the `Group type` is set to private the group will not appear in searches and will require an `invite` to join, even if the group security is set to `open`.

The `group security` options limits the ability for users to join the group.

- **open** - If the group type is set to `public` anyone may search for and join the group.
- **invite** - Users must receive an invite from a user that has write [ACL](https://robinsbackend-robinsbackend-portalx.cloudbackend.cloud/cloudbackend/docs/database/the-singularity/get-to-know/concepts/acl) rights.
- **review** - Users may apply to join the group, but must be approved by a user with write [ACL](https://robinsbackend-robinsbackend-portalx.cloudbackend.cloud/cloudbackend/docs/database/the-singularity/get-to-know/concepts/acl) rights.
- **closed** - No one may join the group.


Once the group has been added it automatically appear and be selected under the Tenant group in the group list. With the group members visible.

## Delete Group

Groups may be deleted with the `Delete...` button or from right clicking the group in the group list. Only the `owner` of the group may delete a group. Any configuration related to the group will be deleted with the group.

> **Warning:** Deleting a group will result in all of its sub-groups being deleted as well as all the data stored on their `databases`.

## Remove Role

### Removing a role from an identity

To remove an assigned role from an identity, click on the role to be removed in the grid displaying the assigned roles for the identity and click the `Delete` button (figure 10).

> **Note:** If you accidentally deleted an assigned role to an identity, you can quickly add back the role to the identity again without any harm being done.


### Removing a role from the tenant

To end this chapter we will look at how to remove a role from the tenant. In the `Manage Roles` application we can select a role that should be removed. After it is highlighted we can click the `Delete` button and the role will be **permanently** removed from the tenant. Figure 11 and 12 display what deletion looks like and the safety prompt that asks if you are really sure you want to remove the role.



> **Warning:** Do not delete a role unless you are sure that the role first has been deleted from the ACLs of important `containers` used in the database(s). Also make sure that there is an identity or other role that has access to containers or `objects` assigned instead of the role to be deleted before doing the delete. You might otherwise end up with objects or containers that only the `Owner` of the tenant may remove or access.

## Role ACLs

### Setting group/tenant ACLs for a role

When a role is created it will show up in the list of the `Manage Roles` application on the left side, while the selected role ACLs permissions relative a group or the tenant (the root group and database) is configured to the right using the grid. A role may be created and left **without any permissions set**, see figure 6, which is how most roles created for identities that are not administrators will look like.

> **Note:** Please note that any identity assigned to the role will have the ability to perform all the actions allowed by the configured ACLs of the role on the group where the role belongs to, but not on any other group.

These ACL permissions given at the group level are quite different from ACL permissions set for the role on a `container` or `object`. This is were a role in most cases is being used, to control access to the database through the use of ACLs on `containers` and `objects`. These important ACLs are configured using the [Database Explorer](https://robinsbackend-robinsbackend-portalx.cloudbackend.cloud/cloudbackend/docs/database/the-singularity/database-overview/database-explorer) properties dialogue and through the `Manage Roles` application.

> **Note:** To login to the tool, the identity needs a role with at least ACL read access to `Roles` and `Identities`.

The above described role permissions in the `Manage Roles` application are more generic and have more to do with the management of the tenant or group, and its respective members. **For most roles these permissions will thereby be set to none**, i.e. the role is given no access to the management of the group or tenant.


Different types of ACLs on the role allows role members to list (**read**) create (**write**) or remove (**delete**) different aspects of the resources on your group. For example, the **read** flag on the ACL type `roles` give the role members ability to list other roles available in the group. The **edit** flag on the ACL type `roles` allows editing the ACLs for that type for other members of the group. Select a permission type in the application to get further information about the type and its use.

> **Tip:** To be able to see the `Role`, the ACL for Roles requires at least **read** permission. To be able to see the `tenant database` or `group database`, the ACL for Identities requires at least **read** permission.

> **Tip:** Any changes are picked up the next time the Members log in again.

**Process Syntax**

