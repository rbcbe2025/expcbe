# Evals

The cases `claude plugin eval` grades (Claude Code 2.1.269 or later): one folder per case, `<skill>-<id>/`, generated by
the repository's `scripts/gen-evals.mjs` from each skill's own evals and never edited here. `mocks/` is hand-written;
`results/` (ignored by git) is where a run writes its report.

## What a case holds

- `prompt.md`: the prompt, verbatim, with the case's frontmatter. Every case may use Read, Glob, Grep, Skill, Write, Edit
  and Bash; the last three are granted by the operator (`--allow-tools`), as `scripts/run-evals.sh` does.
- `graders/assertion-NN.md`: one grader per assertion of the skill's eval, so a run scores the fraction of assertions it
  meets and the report names the ones it missed. Most are `llm` graders over the run's trace (the judge votes three times;
  two passes pass). The assertions about tool calls are `tool_used` or `tool_order` graders instead, from the repository's
  `evals/checks.json`: the judge sees a long run's trace with its middle elided, so a call made mid-run is invisible to it,
  while those graders read every call. A list in `checks.json` splits the assertion into `assertion-NNa.md`,
  `assertion-NNb.md` with half the weight each.
- `graders/uses-skill.md`: a `tool_used` grader for `Skill` on the cases whose prompt names the skill. Under the
  with/without comparison it is an indicator, not part of the score.
- `case.yaml`, `scaffold.sh`, `fixture/`: on the cases whose prompt takes files for granted ("my package", "my app in
  app/", "the upload passed"). The scaffold copies the fixture into the run's working directory before the agent starts
  (`--scaffold`). The fixtures are the repository's `evals/fixtures/` (its README says what each one is).
- `mocks/cloudbackend-tenant/_server.md` on the two sign-in cases: the tenant stand-in starting signed out.

Skipped, with the reason: xios3-app-workflow-12 assertions 1 and 2 (the eval run has no built-in browser tool, and
without one the skill rightly lets `tenant_signin` open the system browser; these points need the Claude desktop app).

## The servers in a run

| Server | In a run | Why |
| --- | --- | --- |
| cloudbackend-tenant | `mocks/cloudbackend-tenant/`: an `agent` stand-in (a model answers each call in the real server's shapes, from `_server.md`'s account `acme` with the project `tasktrack`); `_tools.json` is the real server's tools/list, refreshed by gen-evals | it signs in, uploads and deploys: no run may reach CloudBackend. The stand-in starts signed in (the deploy cases take an earlier sign-in for granted). Its `abort_when` ends the run with score 0 when a password, a token or a key reaches a call, when `enable_deploy_connector` is called (an account change nobody said yes to), or when `upload_project` skips lint |
| cloudbackend-deploy | `mocks/cloudbackend-deploy/`: every tool answers the 401 the real connector gives an account without a sign-in realm | the remote server needs an OAuth sign-in per account |
| cloudbackend-docs, cloudbackend-build | the plugin's real servers (`--allow-real-servers`, their tools granted by name) | this repository's own read-only code: the docs server reads the public portal, the build server lints the files it is given. A mock would make the lookups up |

Agent stand-ins record their answers under `results/<run>/mock-recordings/` with an `ADOPT.txt`; copying a recording into
`mocks/.replay/` (or a case's `mocks/.replay/`) makes later runs replay it without a model call. None are adopted yet.

## Running it

On big (Claude Code 2.1.316): `scripts/run-evals.sh <label> --ablation with-without --runs 3 -j 4 --max-cost-usd 50`
writes `results/<label>.json`, `<label>.log` and an HTML report. The release (stage e) runs it with `--runs 1` when the
skills or the evals changed; on a machine whose Claude Code is older, release with `--skip-evals` and run it on big.
