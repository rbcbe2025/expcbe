# claude-plugin — the CloudBackend developer plugin, and how it is built

The plugin itself is `plugins/cloudbackend/`; its `README.md` is the user-facing one. This repository holds the
marketplace that serves it, the scripts that assemble it from the documentation hub's built outputs and the build
server's package, the configs for other MCP clients, the eval cases, and the release pipeline. Zero dependencies:
Node 22 built-ins, `bash`, `git`, and the `claude` CLI for validation and evals.

## Layout

```
.claude-plugin/marketplace.json     the marketplace "cloudbackend": one plugin, relative source ./plugins/cloudbackend
                                    (the git form, what GitHub serves; entry fields GENERATED from plugin.json)
plugins/cloudbackend/               the plugin
  .claude-plugin/plugin.json        name, version YYYY.MDD.N (pinned), description, userConfig.cbe_tenant (the deploy tenant)
  .mcp.json                         GENERATED: cloudbackend-docs (node, servers/docs), cloudbackend-build (sh
                                    scripts/run-build-server.sh ${CLAUDE_PLUGIN_DATA}: the data directory's venv python,
                                    -m cbemcp_build from servers/build/src), cloudbackend-deploy (CloudBackend's live
                                    server, per tenant from userConfig)
  hooks/hooks.json                  SessionStart → scripts/ensure-build-venv.sh: the build server's Python environment, once
  servers/docs/                     GENERATED by scripts/sync-servers.mjs from the hub's staged documentation server (13 tools)
  servers/build/                    GENERATED by scripts/sync-servers.mjs from the cbemcp-build package (3 tools; src/, requirements.txt)
  skills/<name>/                    GENERATED by scripts/sync-skills.mjs from the hub's built .skill zips
  SKILLS.json                       GENERATED provenance: version, content hash and sha256 per skill
  agents/                           the five XIOS/3 workflow agents (Claude Code only), hand-written
  evals/<skill>-<id>/               GENERATED by scripts/gen-evals.mjs from each skill's evals.json (prompt.md + graders/)
  scripts/connect-deploy.sh         the deploy connector for clients that do not read userConfig
  scripts/ensure-build-venv.sh      the hook script; also what other clients run once by hand
  scripts/run-build-server.sh       the build server's launcher (Claude Code expands ${CLAUDE_PLUGIN_DATA} in args, not in command)
  README.md, LICENSE                install, skills and servers blocks GENERATED between markers
clients/                            GENERATED: cursor/, vscode/, codex/, gemini/ — the two local servers, <plugin-dir> to replace
evals/baselines/                    reference transcripts for the two baseline graders (none recorded yet)
scripts/                            the build and release scripts (below)
dist/                               GENERATED per release, ignored: marketplace.json (archive source), index.json, the zip
_archive/                           superseded files, date-stamped, each with an ARCHIVED.md
RELEASES.md                         one row per release
CLAUDE.md                           the repo contract
```

## Scripts

| Script | Does | Exit 1 when |
| --- | --- | --- |
| `node scripts/sync-skills.mjs [--check]` | Reads the hub's `public/public/skills/index.json`, checks each `.skill` zip's sha256 against it, unpacks into `plugins/cloudbackend/skills/<name>/`, prunes skills the index no longer lists, writes `SKILLS.json`. | a sha256 differs from the index; `--check`: the copy here drifted |
| `node scripts/sync-servers.mjs [--check] [--only docs\|build]` | Copies the documentation server from the hub's `public/dist/mcpb/cloudbackend-docs/server/` and the build server's package from `../mcp-cloudbackend/cbemcp-build` (`CBE_BUILD_SRC`) into `servers/`, each with `VENDORED_FROM` and `MANIFEST.sha256`; never copies caches, environments or `node_modules`; refuses a file naming a workspace path. | a source is not there yet (it prints the path expected); `--check`: a copy drifted |
| `node scripts/bump-version.mjs [--check]` | Sets `plugin.json` (and the marketplace entry) to today's `YYYY.MDD.N` only if `plugins/` differs from the last tag `v<version>`; `.N` counts up within a day. An untagged version is re-dated, not counted. | `--check`: a bump is due |
| `node scripts/gen-clients.mjs [--check]` | Writes `.mcp.json`, the marketplace entry's fields, `clients/*`, the README's install, skills and servers blocks, `dist/marketplace.json` (archive source: the zip's absolute URL on the portal, sha256 filled by `pack.mjs`), `dist/index.json`, and the hub's `public/plugin.json` (version, the three install forms, the `servers` block, the GitHub repository). The base URL is the hub's `public/portal.json` `url` + `/plugin`; the GitHub form is `plugin.json`'s `repository`, else the `mirror` remote's URL, else the placeholder in `lib.mjs`. | no `portal.json`; `--check`: a tracked output would change |
| `node scripts/gen-evals.mjs [--check]` | One case per entry of each skill's `evals.json` in the hub's `_skills/<skill>/evals/`: `prompt.md` (verbatim), `graders/assertions.md` (an `llm` grader over the trace), `graders/uses-skill.md` (`tool_used: Skill`, with-only, where the prompt names the skill), and a `baseline` grader on two cases once their reference transcript is in `evals/baselines/`. | a case has no prompt or assertions; `--check`: the cases drifted |
| `node scripts/guard.mjs` | Runs the hub's publication guard over every text file here: workspace paths, test-tenant hosts (the portal's host allowed under the skills, `servers/docs/`, `dist/`, the READMEs and `RELEASES.md`), the vocabulary's replaced terms and the XIOS/3 spelling in our own text; refuses a top-level `bin/`, `node_modules/`, bytecode caches or environments in the plugin, a remote `.mcp.json` entry other than the per-tenant deploy form, and the deploy host named for anything but `/mcp/<tenant>`. | any finding |
| `node scripts/check-servers.mjs [--deep] [--python <path>]` | `initialize` + `tools/list` over stdio on the documentation server (13 tools, titled and annotated) and, when synced and an environment exists, the build server (3 tools); `--deep` calls `xios3_component("grid")`, which reads the portal; the deploy host's liveness (soft). | a local server is present and does not answer as promised |
| `node scripts/pack.mjs` | The plugin as one deterministic zip, `dist/cloudbackend-<version>.zip` (Unix modes kept, caches and eval results left out), and its sha256 into `dist/index.json` and the marketplace entry. | no manifest, hook or documentation server; a `bin/` in the plugin |
| `scripts/release.sh [--dry-run] [--skip-evals] [--no-portal]` | Stages 0 and a–i: clean trees, build the skills in the hub, sync skills and servers, bump, generate, guard + validate + evals (only when `SKILLS.json` or `evals/` changed since the last tag), pack + commit + tag, copy `dist/{marketplace.json,index.json,<zip>}` into the hub's `public/public/plugin/` (older zips stay) and `git push mirror main --tags` when the `mirror` remote exists, check the servers, deploy the portal, record. | a stage fails; a server source is missing |

## Where things come from

- **The skills:** the documentation hub next to this repo (`../estate-docs`, or `CBE_DOCS_HUB`) builds them with its own
  tooling into `public/public/skills/<name>.skill` plus an `index.json` with each skill's version, content hash and
  sha256. `sync-skills.mjs` copies those zips byte for byte. The hub's skill sources are never read here, with one
  exception: each skill's `evals/evals.json`, its test material, which the hub does not package (`gen-evals.mjs`).
- **The documentation server:** the hub's Claude Desktop extension server, staged by its `scripts/build-mcpb.mjs` at
  `public/dist/mcpb/cloudbackend-docs/server/` with the portal's address filled in and the publication guard run. The
  same files serve Claude Desktop (as the `.mcpb`) and this plugin. It reads the portal over HTTPS and needs no sign-in.
- **The build server:** `cbemcp-build`, the pure Python package extracted from the deploy server's codebase
  (`../mcp-cloudbackend/cbemcp-build`): `lint_project`, `scaffold_project`, `benchmark_project` with the tenant grammar,
  the schemas and the design kit. `python -m cbemcp_build` serves stdio. The plugin carries it under `servers/build/src/`;
  the hook installs `requirements.txt` into `${CLAUDE_PLUGIN_DATA}/venv` once (Python 3.12 or `uv` needed).
- **The deploy connector:** CloudBackend's live per-tenant server, `https://mcp.cloudbackend.com/mcp/<tenant>`, the
  tenant from `plugin.json`'s `userConfig` in Claude Code and by hand elsewhere. Nothing else of ours is on that host.
- **The portal's address:** the hub's `public/portal.json`. The marketplace, index and zip the portal serves live at
  `<portal>/plugin/`; `gen-clients.mjs` derives every URL from it, and `release.sh` copies the files into the hub's
  `public/public/plugin/` for the portal build to publish.

The hub's `_tools/boundary.json` lists this repo as a consumer (reads the built skills, `portal.json`, the staged server;
writes `public/plugin.json` and `public/public/plugin/`; checked by the weekly job's 4.4, never imported).

## Versioning and releases

The plugin's version is pinned in `plugin.json` as `YYYY.MDD.N` (2026-11-04 → `2026.1104.0`, a second release that
day → `2026.1104.1`) and wins over the marketplace entry and the commit. A release is the tag `v<version>`.
`scripts/release.sh` runs the stages in order; `--dry-run` prints every stage's commands and runs nothing.

Two marketplaces serve the same plugin: the private GitHub repository (the `mirror` remote; `main` = what testers get,
`dev` = work) with the relative source, and the portal's `plugin/marketplace.json` with an archive source (a marketplace
added by URL cannot resolve a relative path, so it points at the zip's absolute URL and pins its sha256).

## For testers (a private marketplace)

- Install once: `claude plugin marketplace add <org>/claude-plugin`, then `claude plugin install cloudbackend@cloudbackend`
  (the GitHub form follows the `mirror` remote). The install asks for the CloudBackend tenant.
- A private repository needs a GitHub credential Claude Code can use without prompting: an SSH key loaded in
  `ssh-agent` (the shorthand probes `ssh -T git@github.com` and clones over SSH when it answers), or
  `gh auth login` + `gh auth setup-git` with `CLAUDE_CODE_PLUGIN_PREFER_HTTPS=1` set in the shell. Check this on each
  tester's machine at onboarding; a missing credential makes updates stop silently.
- Updates: `claude plugin marketplace update cloudbackend`, then `claude plugin update cloudbackend@cloudbackend`; or
  switch auto-update on for the marketplace under `/plugin` → Marketplaces (off by default for a marketplace you added).
- The build server needs Python 3.12 or `uv`; the first session may show `cloudbackend-build` as disconnected until
  the session-start hook finishes (it prints one line). Without either, the hook says so and the workflow skill runs
  those steps as checklists.
- Never rename the plugin or the marketplace: `cloudbackend@cloudbackend` is what every install is keyed on.

## Rules

See `CLAUDE.md`: never edit the generated trees by hand; the hub's built outputs only (plus the skills' evals.json);
commit here, push only `mirror`; archive, never delete; XIOS/3, XVM, CloudBackend PaaS.
