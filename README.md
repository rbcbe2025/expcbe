# claude-plugin — the CloudBackend developer plugin, and how it is built

The plugin itself is `plugins/cloudbackend/`; its `README.md` is the user-facing one. This repository holds the
marketplace that serves it, the scripts that assemble it from the documentation hub's built outputs, the connector
configs for other clients, and the release pipeline. Zero dependencies: Node 22 built-ins, `bash`, `git`, and the
`claude` CLI for validation.

## Layout

```
.claude-plugin/marketplace.json     the marketplace "cloudbackend": one plugin, relative source ./plugins/cloudbackend
plugins/cloudbackend/               the plugin
  .claude-plugin/plugin.json        name, version YYYY.MDD.N (pinned), description, homepage, licence, keywords
  .mcp.json                         the two hosted connectors (docs, build); the deploy connector is per tenant
  skills/<name>/                    GENERATED by scripts/sync-skills.mjs from the hub's built .skill zips
  SKILLS.json                       GENERATED provenance: version, content hash and sha256 per skill
  agents/                           the workflow agents (Claude Code only); empty until the workflow skill lands
  evals/                            eval cases for `claude plugin eval`; empty until the workflow skill lands
  scripts/connect-deploy.sh         adds the per-tenant deploy connector
  README.md, LICENSE                install block and skills table GENERATED between markers
clients/                            GENERATED: cursor/ (mcp.json, DEEPLINK.md), vscode/, codex/, gemini/
scripts/                            the build and release scripts (below)
dist/                               GENERATED per release, ignored: the hosted marketplace.json, index.json, the zip
RELEASES.md                         one row per release
CLAUDE.md                           the repo contract
```

## Scripts

| Script | Does | Exit 1 when |
| --- | --- | --- |
| `node scripts/sync-skills.mjs [--check]` | Reads the hub's `public/public/skills/index.json`, checks each `.skill` zip's sha256 against it, unpacks into `plugins/cloudbackend/skills/<name>/`, prunes skills the index no longer lists, writes `SKILLS.json`. | a sha256 differs from the index; `--check`: the copy here drifted |
| `node scripts/bump-version.mjs [--check]` | Sets `plugin.json` (and the marketplace entry) to today's `YYYY.MDD.N` only if `plugins/` differs from the last tag `v<version>`; `.N` counts up within a day. An untagged version is re-dated, not counted. | `--check`: a bump is due |
| `node scripts/gen-clients.mjs [--check]` | Writes `clients/*`, the README install block and skills table, `dist/marketplace.json` (archive source pointing at the hosted zip), `dist/index.json`, and the hub's `public/plugin.json` for the portal's Tools page. | `--check`: a tracked output would change |
| `node scripts/guard.mjs` | Runs the hub's publication guard over every text file here: workspace paths, test-tenant hosts (the portal's host allowed under `skills/` only), the vocabulary's replaced terms and the XIOS/3 spelling in our own text; also refuses a top-level `bin/` or `node_modules/` in the plugin. | any finding |
| `node scripts/check-hosted.mjs [--pull]` | `tools/list` over HTTPS on both connectors; `/docs/health` corpus dates against the hub's `toc.json`. `--pull` is a stub for the weekly log merge. | a connector is unreachable (a corpus date behind is a soft finding) |
| `node scripts/pack.mjs` | The plugin as one deterministic zip, `dist/cloudbackend-<version>.zip`, and its sha256 into `dist/index.json`. | no manifest, or a `bin/` in the plugin |
| `scripts/release.sh [--dry-run] [--skip-evals] [--no-portal]` | Stages 0 and a–i: clean trees, build the skills in the hub, sync, bump, gen-clients, guard + validate + evals, pack + commit + tag, hosted connectors, portal, record. Stages that need the host print the hand-off. | a stage fails |

## Where the skills come from

The documentation hub checked out next to this repo (`../estate-docs`, or `CBE_DOCS_HUB`) builds the skills with its own
tooling into `public/public/skills/<name>.skill` plus an `index.json` with each skill's version, content hash and
sha256. `scripts/sync-skills.mjs` is the only way a skill enters this plugin, and it copies those zips byte for byte.
The hub's skill sources are never read here, and nothing in this repo is ever read into the hub's corpora.

**Open:** the hub's `_tools/boundary.json` lists every path outside the hub that its tooling may touch. It needs a
`consumers` entry for this repo ("reads `public/public/skills/*.skill` and `index.json`, the guard module and the
vocabulary; writes `public/plugin.json` and `_reports/plugin/`; checked by the weekly job's 4.4, never imported").
Adding it is Robin's call; until then the hub's weekly consumer check does not know this repo exists.

## Versioning and releases

The plugin's version is pinned in `plugin.json` as `YYYY.MDD.N` (2026-11-04 → `2026.1104.0`, a second release that
day → `2026.1104.1`) and wins over the marketplace entry and the commit. A release is the tag `v<version>`. Claude Code
does not auto-update plugins from a marketplace added by URL, so users run `claude plugin update cloudbackend@cloudbackend`.

`scripts/release.sh` runs the stages in order; `--dry-run` prints every stage's commands and runs nothing. The hosted
copies (`marketplace.json` with an archive source, `index.json`, the zip) are served from
`https://mcp.cloudbackend.com/plugin/`; copying them there is a hand-off until this machine has access to the host
(`RELEASE_PUBLISH_TARGET=user@host:/path` makes stage f `scp` them).

## Rules

See `CLAUDE.md`: never edit `skills/` by hand; the hub's built outputs only; commit here, never push; archive, never
delete; XIOS/3, XVM, CloudBackend PaaS.
