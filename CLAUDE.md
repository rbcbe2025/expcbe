# claude-plugin — repo contract

This repository builds and releases the CloudBackend developer plugin for Claude (`plugins/cloudbackend/`). It is its
own git root under the CloudBackend group. `README.md` here explains the layout and the scripts; the plugin's own
`README.md` is what users read.

## Rules

- **Never edit `plugins/cloudbackend/skills/`, `SKILLS.json`, `servers/docs/` or `evals/<case>/` by hand.** They are
  generated: the skills by `node scripts/sync-skills.mjs` from the documentation hub's built skills
  (`public/public/skills/index.json` and the `.skill` zips next to it, checked out at `../estate-docs` or `CBE_DOCS_HUB`);
  the documentation server by `node scripts/sync-servers.mjs` from the hub's staged
  `public/dist/mcpb/cloudbackend-docs/server/` (with a `VENDORED_FROM` and a `MANIFEST.sha256`); the eval cases by
  `node scripts/gen-evals.mjs`. A fix is made at the source, rebuilt there, then synced here. Every sync has a `--check`
  that says when the copy drifted.
- **`servers/build/` is authored here.** `index.mjs` is the zero-dependency Node port of the deploy server's Python
  build tools (`lint_project`, `benchmark_project`; the Python package stays the server-side implementation behind
  the deploy connector). It reads the rule table from the plugin's own `skills/xios3-app-workflow/references/tenant-grammar.json`
  at run time, so the grammar has one source inside the plugin; a rule change is made in the hub's skill and synced.
  `node --test plugins/cloudbackend/servers/build/test.mjs` must stay green (the seeded traps, every rule, the stdio
  session); `release.sh` runs it. ASCII only, no dependencies, nothing installed on the user's machine beyond Claude Code.
- **What this repo reads outside itself, and nothing else:** the hub's built outputs (`public/public/skills/`,
  `public/portal.json` for the portal's address, the staged documentation server, `<corpus>/toc.json`), the hub's
  guard module `public/scripts/extension/guard.mjs` with `_tools/publication-guard.json` and `_vocabulary/terms.json`,
  and the hub's `_skills/<skill>/evals/evals.json` (the skills' own test material, the one read under `_skills/`, because
  the hub does not build it into the packages). It writes the hub's `public/plugin.json` and, at release,
  `public/public/plugin/`. No other project in the workspace is ever read by a script here (the Python build tools were
  read once, by hand, to write the port; see `_archive/2026-11-04-python-build-server/`).
- **The servers run inside the plugin with `node`; CloudBackend's deploy host is used for one thing.** `.mcp.json`
  (generated by `gen-clients.mjs` from `lib.mjs`'s `SERVERS`) runs `servers/docs/index.mjs` and `servers/build/index.mjs`
  with `node`: no hook, no environment, no `${CLAUDE_PLUGIN_DATA}`. The deploy connector is
  `https://mcp.cloudbackend.com/mcp/${user_config.cbe_tenant}`, the tenant from `plugin.json`'s `userConfig` (Claude
  Code asks at install; `scripts/connect-deploy.sh` serves the clients that do not). Nothing may name that host beyond
  its `/mcp/<tenant>` form; `guard.mjs` refuses it.
- **Commit here; push only `mirror`.** The private GitHub repository is `rbcbe2025/expcbe` (`plugin.json`
  `repository`); it is the `mirror` remote, and `release.sh` pushes `main` and the tags there. `main` is what testers get; work
  happens on `dev` and merges to `main` per release. No other remote, ever. **Never rename the plugin** (`cloudbackend`,
  `cloudbackend@cloudbackend`): a published plugin's name is its identity for every install.
- **Archive, never delete.** Superseded files move to `_archive/<date>-<what>/` with an `ARCHIVED.md`. Generated
  trees (`skills/`, `servers/docs/`, `evals/<case>/`, `clients/`, `dist/`) are regenerated, not archived.
- **`.mcp.json`, the marketplace entry, `clients/`, the README's install, skills and servers blocks, `dist/`, and the
  hub's `public/plugin.json` are generated** by `node scripts/gen-clients.mjs`; the plugin's base URL is the portal's
  address + `/plugin`, the GitHub form is `plugin.json`'s `repository` (`rbcbe2025/expcbe`), else the `mirror` remote, else `lib.mjs`'s placeholder. Edit the generator.
- **The version is pinned** in `plugins/cloudbackend/.claude-plugin/plugin.json` (`YYYY.MDD.N`) and bumped only by
  `node scripts/bump-version.mjs`, which moves it only when `plugins/` differs from the last release tag `v<version>`.
- **`node scripts/guard.mjs` must report 0 problems** before any commit that touches `plugins/` or `clients/`: no
  workspace paths, the portal's test-tenant host only where the plugin is served from or reads the portal (the skills,
  `servers/docs/`, `dist/`, the READMEs, `RELEASES.md`), no caches or environments in the plugin, no hosted `/docs`,
  `/build` or `/plugin` on the deploy host, and XIOS/3 spelled that way in our own text.
- **Nothing to install beyond Claude Code.** Robin's decision of 2026-11-04: the plugin starts on every machine
  with Claude Code alone, so a server that needs a runtime other than Node does not go in.
- **Product names:** XIOS/3, always with the slash and the digit (the guard refuses the shortened spellings), XVM is
  the XML Virtual Machine, the product is CloudBackend PaaS, CBE is CloudBackend.
- Releases run `scripts/release.sh` by hand, on big, after review (`--dry-run` first). Stages that need what is not
  there (the mirror remote, a server source) print a hand-off or stop. Each release adds a row to `RELEASES.md`.
