# claude-plugin — repo contract

This repository builds and releases the CloudBackend developer plugin for Claude (`plugins/cloudbackend/`). It is its
own git root under the CloudBackend group. `README.md` here explains the layout and the scripts; the plugin's own
`README.md` is what users read.

## Rules

- **Never edit `plugins/cloudbackend/skills/`, `SKILLS.json`, `servers/` or `evals/<case>/` by hand.** They are
  generated: the skills by `node scripts/sync-skills.mjs` from the documentation hub's built skills
  (`public/public/skills/index.json` and the `.skill` zips next to it, checked out at `../estate-docs` or `CBE_DOCS_HUB`);
  the servers by `node scripts/sync-servers.mjs` (the documentation server from the hub's staged
  `public/dist/mcpb/cloudbackend-docs/server/`, the build server from `../mcp-cloudbackend/cbemcp-build` or
  `CBE_BUILD_SRC`, each with a `VENDORED_FROM` and a `MANIFEST.sha256`); the eval cases by `node scripts/gen-evals.mjs`.
  A fix is made at the source, rebuilt there, then synced here. Every sync has a `--check` that says when the copy drifted.
- **What this repo reads outside itself, and nothing else:** the hub's built outputs (`public/public/skills/`,
  `public/portal.json` for the portal's address, the staged documentation server, `<corpus>/toc.json`), the hub's
  guard module `public/scripts/extension/guard.mjs` with `_tools/publication-guard.json` and `_vocabulary/terms.json`,
  the hub's `_skills/<skill>/evals/evals.json` (the skills' own test material, the one read under `_skills/`, because the
  hub does not build it into the packages), and the build server's package. It writes the hub's `public/plugin.json`
  and, at release, `public/public/plugin/`. No other project in the workspace is ever read by a script here.
- **The servers run inside the plugin; CloudBackend's deploy host is used for one thing.** `.mcp.json` (generated by
  `gen-clients.mjs` from `lib.mjs`'s `SERVERS`) runs the documentation server with `node` and the build server through
  `scripts/run-build-server.sh`, from a Python environment the `SessionStart` hook (`hooks/hooks.json` →
  `scripts/ensure-build-venv.sh`) creates in `${CLAUDE_PLUGIN_DATA}` (the launcher exists because Claude Code expands
  that variable in a server's args and env, not in its command; measured on 2.1.316). The deploy connector is `https://mcp.cloudbackend.com/mcp/${user_config.cbe_tenant}`, the
  tenant from `plugin.json`'s `userConfig` (Claude Code asks at install; `scripts/connect-deploy.sh` serves the clients
  that do not). Nothing may name that host beyond its `/mcp/<tenant>` form; `guard.mjs` refuses it.
- **Commit here; push only `mirror`.** The private GitHub repository Robin names is added as the `mirror` remote
  (`git remote add mirror …`) and `release.sh` pushes `main` and the tags there. `main` is what testers get; work
  happens on `dev` and merges to `main` per release. No other remote, ever. **Never rename the plugin** (`cloudbackend`,
  `cloudbackend@cloudbackend`): a published plugin's name is its identity for every install.
- **Archive, never delete.** Superseded files move to `_archive/<date>-<what>/` with an `ARCHIVED.md`. Generated
  trees (`skills/`, `servers/`, `evals/<case>/`, `clients/`, `dist/`) are regenerated, not archived.
- **`.mcp.json`, the marketplace entry, `clients/`, the README's install, skills and servers blocks, `dist/`, and the
  hub's `public/plugin.json` are generated** by `node scripts/gen-clients.mjs`; the plugin's base URL is the portal's
  address + `/plugin`, the GitHub form is `plugin.json`'s `repository`, else the `mirror` remote, else `lib.mjs`'s placeholder. Edit the generator.
- **The version is pinned** in `plugins/cloudbackend/.claude-plugin/plugin.json` (`YYYY.MDD.N`) and bumped only by
  `node scripts/bump-version.mjs`, which moves it only when `plugins/` differs from the last release tag `v<version>`.
- **`node scripts/guard.mjs` must report 0 problems** before any commit that touches `plugins/` or `clients/`: no
  workspace paths, the portal's test-tenant host only where the plugin is served from or reads the portal (the skills,
  `servers/docs/`, `dist/`, the READMEs, `RELEASES.md`), no bytecode caches or environments in the plugin, no hosted
  `/docs`, `/build` or `/plugin` on the deploy host, and XIOS/3 spelled that way in our own text.
- **The build server needs Python 3.12 or `uv` on the user's machine.** The hook installs once and says so in one
  line; the first session may show `cloudbackend-build` disconnected until it finishes. That sentence stays in the
  plugin README and on the launch page.
- **Product names:** XIOS/3, always with the slash and the digit (the guard refuses the shortened spellings), XVM is
  the XML Virtual Machine, the product is CloudBackend PaaS, CBE is CloudBackend.
- Releases run `scripts/release.sh` by hand, on big, after review (`--dry-run` first). Stages that need what is not
  there (the mirror remote, a server source) print a hand-off or stop. Each release adds a row to `RELEASES.md`.
